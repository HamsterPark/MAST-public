# 运行规则

下面这十二条规则也由 `GET /guide` 的 JSON `rules` 数组返回，给完全不读这份文件的 agent 用；
它们的 `id` 值得记住，因为 API 的拒绝有时会直接点它的名字。十二条之后是那些放不进这份
短清单的操作性规则，每条都附着理由 —— 它们涉及的机制见[概念](02-concepts.md)。

## 十二条规则

| ID | 规则 | 为什么 |
|---|---|---|
| `briefing-first` | 先读简报 | `GET /briefing` 带着 MAST 自己的 agent 每一轮都能看到的东西：针尖、仪器档案、实时读数、操作员偏好、续工块、所有人最近的动作、你发出的请求。 |
| `scope-before-data` | 先定实验与样品再产数据 | 先选定或新建实验与样品。产数据技能需要样品作用域；实验动作入账需要当前实验与可用存储。检查每个作业的 `recorded` 回执。 |
| `find-by-action` | 按动作找技能 | 按你要的动作检索，不要猜名字；技能是按它解决的问题命名的。执行前读技能卡：单位、范围、前置条件、这台仪器上的实测耗时。 |
| `jobs-not-timeouts` | 用作业跑技能 | 提交然后轮询。客户端超时不等于失败：技能还在跑、还占着仪器。提交丢了就用同一个 `request_id` 重发，绝不换新的。 |
| `busy-means-wait` | 撞锁就是别人在开车 | `refused_busy` 表示另一条链路正占着仪器。立刻重试不会让它更快结束：等它，或者问操作员。 |
| `how-to-stop` | 怎么停 | 取消在作业下一次协作检查时生效。用停止技能请求物理停止（不受仪器锁限制），出现危险时使用急停，并检查响应与仪器状态。解除急停闩由操作员决定。 |
| `three-states` | ok、success、degraded 是三件事 | 技能失败不是端点错误；degraded（某个子系统没接线）不是「空」。三者都看完再下结论。 |
| `operating-mode` | 运行模式是操作员定的 | SAFE 在自主执行路径上拒绝针尖处理，包括外部作业和组合子步骤。不要绕过或修改；需要针尖处理就问操作员。 |
| `no-proxy-approval` | 不替操作员拍板 | 不要替操作员批准或处理任何需要人决定的提示。问了之后等答复。 |
| `after-restart` | 重启之后先看再动 | 服务重启时还在跑的作业标为 `lost_on_restart`，绝不重放。先读简报弄清仪器处在什么状态。 |
| `raw-data` | 用服务端给的帧 | 扫描图从数据端点取：服务端已经把朝向约定（反向扫描的镜像、扫描方向的翻转）一次处理对了。 |
| `leave-a-trail` | 留下痕迹 | 结论写成笔记；MAST 自己的 agent 会召回它们。结束时写交接，并让仪器空闲：没有在跑的作业、扫描已停。 |

## 怎么停，精确地说

开始一次粗动之前，先停掉任何在跑的扫描，并且等它真的停下来 —— 这两件事绝不能重叠。
请求物理停止时，跑一个停止类技能，比如 `StopScan`（仪器锁从不拦它），或者调急停端点
打一次完整的 E-STOP；然后取消那个作业本身，让它自己的记录如实反映出你要求它停止。
尝试向硬件发送停止动作的是停止技能或急停调用，应检查结果并确认仪器状态；单靠取消只在作业下一次协作式检查处才生效，
对一个已经卡在单条 Nanonis 命令里的调用毫无作用。

停止类或撤回类技能同样不受并发作业上限约束，所以提交这一类技能永远不会因为别的作业正在
跑而被 `429` 拒绝。但急停闩本身一旦置位，任何作业 —— 停止类技能也不例外 —— 都会在开始
之前就被拒。闩是在硬件停止/退针尝试之前置位的，因此要检查急停响应的 `errors` 和 `retracted`，
不能据此假定成功。若停止尚未确认，立即联系操作员，按仪器本地停止规程处理；操作员核实恢复条件后再解除闩。

## agent 执行环境里的长任务

当你自己的执行环境要派生一个会长时间驱动仪器的任务时，直接起解释器或可执行文件，而不是
经一层 shell 包装脚本：停掉包装脚本不会停掉真正占着仪器的那个孙进程，而一个卡在等待循环
里的包装脚本无论你本想停什么，都可能径自推进到它的下一条命令。同样的道理，也不要用
`nohup` 起它 —— 你需要的是真正能停下你启动的东西的能力，而不只是不再盯着它。

## 中断之后

如果一个长任务被中断了 —— 你的执行环境被杀、连接断了、驱动它的进程被从外部停掉 ——
不要假设仪器还停在你离开时的地方。某个错误处理可能已经把针尖退了出来，或者最后一条命令
可能让它停在运动途中。客户端断连不会取消服务端作业，应先查询原来的 `job_id`；服务重启时尚未结束的作业
才会标成 `lost_on_restart`，且不会重放。重新读简报，包括每段的 `ok`、`degraded` 列表与 `live.stale`；
简报读数来自缓存。若当前仪器状态仍不明确，继续之前应请操作员核实。

## 改完偏压之后

改完偏压之后，成像或跑谱学之前，先等压电蠕变稳下来。稳定所需的时间是这台仪器特有的：
去问操作员，或者查简报里操作员偏好那一段。不要自己往技能调用里填一个数 —— 一个看着合理
却不适合这台仪器的常数，比直接问更糟。

## human-in-the-loop 那几个点

一个组合技能里可能有一步只有人能处理。在外部 agent 这条路径上，没有人在等着接住那次
暂停，所以调用会直接失败 —— `refused_by: needs_human_node` —— 而不是真的等着：一次
没人负责去留意的暂停不是等待，是卡死。如果背后那件事确实需要一个人，改到 MAST 自己的
界面里跑，或者去问操作员，同时继续做你能做的其他事，等答复。不管哪种情况，都不要替
操作员批准、驳回或以任何方式处理一个 human-in-the-loop 提示 —— 包括那些属于 MAST 自己
内部 agent 的提示。那个决定属于一个人，不属于你。

## SAFE 模式不是拦你的墙

SAFE 拦截自主针尖处理，包括外部作业与组合子步骤。它由操作员设置，不能通过本 API 修改。
认证覆盖整个服务，同一份凭据可能也能到达应用的其他端点；SAFE 不是独立的访问权限边界。
应遵守操作员选择的模式与任务范围，不通过其他端点改变它们。
