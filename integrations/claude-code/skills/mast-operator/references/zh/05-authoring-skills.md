# 造技能

按一架不高的梯子往下走，走到第一级能解决问题的地方就停。如果一个官方技能已经做了你
要的事，用它 —— 先搜索，[运行规则](03-operating-rules.md) 里说过这一点。如果一串官方
技能拼起来就能做到，造一个**组合技能**：一份 JSON 图，不是代码，走的闸门与
[概念](02-concepts.md) 里说的完全一样。只有当组合已有技能确实表达不了你要的东西 ——
通常是因为没有技能包过某条 Nanonis 命令 —— 才去提议一个新的 **Python 技能**，交给人审。
这一篇涵盖这两条轨道。

## 组合技能

组合技能是数据：一份 JSON 格式的 `CompositeSpec`，描述一张由已有技能组成的图，由同一个
共用解释器校验与执行。它生效的安全级是它声明的级别与它最严格那一步之间更严的一个，它的
能力标签是所有步骤标签的并集（见[概念](02-concepts.md)）——所以组合打不开任何一扇它的
每一步单独也打不开的门。

### 先起草，再保存

`POST /composites/draft` 校验一份 spec，不保存也不注册任何东西，把所有问题一次性给你，
如果你草稿里的步骤已经被某个现成的官方组合覆盖了，还会附一句提示 —— 值得在动手重造一遍
之前先读。发 `spec: "?"` 能直接从 MAST 拿到格式说明，不用自己去猜。

`POST /composites` 保存一份已校验的 spec 并以你的署名（`ext:<actor>`）热注册：从那一刻起
它就像任何其他技能一样，经 `POST /jobs` 执行。覆盖你自己之前存过的版本需要
`base_version` —— 你上次读到的那个版本号 —— 作为乐观锁；再存一遍完全相同的内容不会
产生一个没有意义的新版本。一个由人（而不是 agent）造的组合技能永远不会这样被覆盖：
换个名字另存一份。

### spec 的格式

一份 spec 有 `name`、`safety_level`、一份 `params` 列表、一份 `nodes` 列表。在这条轨道上
允许的节点类型纯粹是结构性的：`step`、`if`、`loop`、`try`、`set`、`succeed`、`fail`、
`break`、`continue` —— human、LLM 与委托给 agent 的节点在这里都用不了。带 `finally` 体的
`try` 节点用于普通完成或失败时的收尾。硬中断（`GeneratorExit`）会跳过这段收尾，进程终止也不能保证它执行。
即使收尾已执行，仍要核实硬件返回；存在 `finally` 块不能证明针尖已经退回。

三条规则让表达式好读：一步的结果用它自己的 `id` 按**下标**引用（`s1['bias_v']`，`s1` 是
某个 `step` 节点的 id；`last` 指最近跑过的那一步）——属性访问如 `s1.data.x` 不被接受。
每一个 `cond`、`count`、`value` 都是**表达式字符串**，不是字面量 —— 写 `"3"`，不是 `3`。
把一个工作流参数传给某一步用 `{"$expr": "param_name"}`；字面量则直接写。一份不带分支、
引用三个只读步骤各自输出的最小 spec，长这样：

```json
{
  "name": "ExampleReadSequence",
  "safety_level": "auto",
  "params": [],
  "nodes": [
    {"type": "step", "id": "s1", "skill": "GetBias", "params": {}},
    {"type": "step", "id": "s2", "skill": "GetSetpoint", "params": {}},
    {"type": "step", "id": "s3", "skill": "GetCurrent", "params": {}}
  ],
  "outputs": [
    {"name": "bias_v", "expr": "s1['bias_v']"},
    {"name": "setpoint_a", "expr": "s2['setpoint_a']"},
    {"name": "current_a", "expr": "s3['current_a']"}
  ]
}
```

### 会被拒绝的情况

| 情况 | 为什么被拒 |
|---|---|
| spec 里一个 `step` 节点都没有 | 它不会对仪器做任何事，却仍然报告成功 —— 没有用。 |
| spec 只有一个 step、没有任何分支/循环/重试 | 它只是给自己包的那一个技能换了个名字，没有添加任何东西；直接调那个技能。 |
| `human`、`llm` 或 `agent` 节点 | 这条轨道上只开放上面列出的那些结构性节点类型。 |
| 循环体里有触硬件的步骤、却没写 `max_iter` | 默认上限大到能无人值守地跑一整夜；这里触硬件的循环必须声明一个不超过 100 的上限。 |
| 某一步点名的技能在本机是关闭的 | 把一个关闭的技能包进组合技能不会让它重新打开 —— 那是操作员的决定。 |
| 名字已经被一个已注册技能占用，或者与内置模板同名 | 重用这个名字会悄悄顶替那个技能，或者下次 MAST 启动时又被它顶替回去。 |

### 组合技能只能引用官方技能

启动时 MAST 按固定顺序注册技能：先内置技能，然后是存储的组合 spec，然后是 agent 工具，
然后是自定义技能，最后是覆盖层。你保存的 spec 会作为一份存储 spec 被校验、注册 ——
这发生在自定义技能与 agent 工具都还不存在的时候 —— 所以一步点名了其中任何一个都会被拒，
每次启动都一样，只留下一行日志。只能用内置原子技能或其他官方组合技能来搭建。

## Python 技能提议

`POST /skills/proposals` 是最后一招：为一个全新的原子技能写源码，落盘到本机的自定义技能
文件夹**待人审阅**——不会有任何东西被注册或执行。汇报你提议了什么、为什么，然后继续用
已有的东西做手上的事；不要等它。

让一份提议真正生效完全是操作员的决定：他们审阅代码、把它的名字加进启用清单、重启
MAST。那份清单按提议的**文件名主干**认领一份提议，不是按代码里写的类名，所以起名字要
对上，否则启用那一步会去找一个不存在的文件。MAST 在文件里找到的**第一个** `BaseSkill`
子类才会被注册 —— 同一文件里的第二个类会被悄悄忽略 —— 所以一个文件只放一个技能。

### 拒绝名单

同一份静态拒绝名单会跑两次：一次在你提议代码的时候，一次在操作员的 MAST 启用之后加载
它的时候，所以一份先通过了第一次检查、之后又被手改到通不过第二次的文件，会被直接跳过，
只留一行日志。它拦下 `os`、`pathlib`、`socket` 这类模块的导入；`eval`、`exec`、`getattr`
等几个调用；以及任何 dunder 名字或属性访问 —— 为的是堵住常见的沙箱逃逸手法。最后这条
拦得很宽，会把一个普通写法和它针对的那些逃逸手法一起拦下：`super().__init__()` 本身就是
一次被禁止的 dunder 属性访问，所以写技能时不要依赖它。

### 合规报告

每一份提议的回执都带着一份合规报告 —— 与一份社区投稿要过的检查完全相同（是否显式声明
了安全级、拒绝名单、参数单位与范围、这个技能的足迹能不能被分类，等等）——这样你不用等
人指出来，就能确切读到该改哪里。同一套检查也能在一份代码检出上对着磁盘上的文件从命令行
跑，如果你想在提议之前自己先跑几轮：见[投稿技能](06-contributing-skills.md)。
